本数据集包含 5 组精心构造的"对抗样例"，每组针对一个常见的实现错误或隐患。所有样例均可在秒级内完成测试，适合作为回归测试的一部分。

```bash
    ./build/CampusNavigation.exe \

    ./build/test_outputs_adversarial

```

## 用例 A：等代价多解 — `A_equal_cost`

### 图结构

```
P001 ──5── P002 ──5── P004   (路径 1: 总代价 10)
  \                        /
   └──5── P003 ──5──┘        (路径 2: 总代价 10)
```

### 这组数据特殊在什么地方

两条从 P001 到 P004 的路径具有**完全相等的总距离和总时间**（DIST=10, TIME=10），但经过不同的中间节点（P002 vs P003）。不存在任何客观标准区分孰优孰劣——算法必须依靠自身的内部规则做出选择。预期输出固定为 P001→P002→P004（P002 的 ID 字典序小于 P003）。

### 它能卡住哪类错误实现

| 错误类型 | 说明 |
|---------|------|
| 非确定性优先队列 | 若 Dijkstra 使用的优先队列在等代价时不保证顺序，输出可能在两条路径间随机切换，导致相同输入产生不同输出 |
| 哈希表遍历顺序 | 若邻接表用 `unordered_map` 存储且遍历顺序不稳定，松弛同代价邻居的先后顺序不确定 |
| 浮点权重 | 若距离用浮点数存储，`5.0 == 5.0` 可能因精度问题被误判为不等，从而"打破"本应相等的代价 |

### 我的程序如何正确处理

Dijkstra 优先队列使用 `std::priority_queue<PQElement, ..., std::greater<>>`，其中 `PQElement = std::pair<int, std::string>`（累计成本, 顶点 ID）。当累计成本相同时，`std::pair` 的比较运算符自动用第二字段（顶点 ID 的字典序）作为次级键排序。因此在 P002 和 P003 成本相同时，P002（ID 更小）总是先出队并先松弛边，使得路径 P001→P002→P004 成为唯一的、确定性的结果。

### 测试结果

```
PASS — 程序稳定输出 P001→P002→P004
```

## 用例 B：必经点顺序 — `B_mustpass_order`

### 图结构

```
P001 ──1── P002 ──1── P003 ──1── P004   (简单链)
```

### 测试命令

| 命令 | 必须顺序 | 预期代价 | 预期路径 |
|------|---------|---------|---------|
| `MUST_PASS P001 P004 DIST 2 P002 P003` | 先 P002 后 P003（顺向） | 3 | P001,P002,P003,P004 |
| `MUST_PASS P001 P004 DIST 2 P003 P002` | 先 P003 后 P002（逆向） | **5** | P001,P002,P003,P002,P003,P004 |

### 这组数据特殊在什么地方

线形链 P001→P002→P003→P004 上，必经点 P002 和 P003 只有一种空间排列。正向顺序 `P002 P003` 与链路方向一致，代价为 3；反向顺序 `P003 P002` 在物理上**必须先经过 P002 才能到达 P003**，因此执行"先去 P003 再去 P002"时路径必须折返——先走到 P003（途经 P002），再退回 P002，再走向终点（再次途经 P003）。节点在路径中重复出现，总代价从 3 跃升至 5。

### 它能卡住哪类错误实现

| 错误类型 | 说明 |
|---------|------|
| **全排列而非顺序分段** | 若实现将必经点集合做全排列、对每种排列计算路径后取最短，会得到正向结果（代价 3），**错误地忽略用户指定的顺序** |
| 必经点自动排序 | 若实现先将必经点按 ID 升序或其他规则排序后再分段，同样会破坏用户指定的顺序语义 |
| 去重后分段 | 若实现先对必经点列表去重（如连续相同节点）再分段，可能改变语义 |

### 我的程序如何正确处理

`mustPassPath` 预先将 `{from, mustPass..., to}` 拼接为完整点序列，然后**严格按序列顺序逐段调用 Dijkstra**，每段终点作为下段起点。连接时跳过重复的段间节点（前一段末节点 = 后一段首节点）。整个过程不调整、不排序、不去重必经点列表，确保用户指定的访问顺序被原样执行。

### 测试结果

```
PASS — 程序严格按顺序分段，逆向必经过给出代价 5 的路径（含回溯）
```

## 用例 C：时刻边界 — `C_time_boundary`

### 这组数据特殊在什么地方

P001 的 `open_time = close_time = 12:00`，即**一天中仅在 12:00 这一瞬间开放**。这是规范允许的极端情况（`open_time ≤ time ≤ close_time`，等号成立时该时刻开放）。通常的"早 X 点到晚 Y 点"设计不会触及此边界，但正确的实现必须能处理它。

```
P001(仅12:00开放) ──10── P002(全天开放)
```

| 时间 | 预期 | 原因 |
|------|------|------|
| `12:00` | `PATH DIST 10` | P001 在 12:00 开放（`12:00 ≤ 12:00 ≤ 12:00`） |
| `11:59` | `NO_PATH` | P001 未到开放时间 |
| `12:01` | `NO_PATH` | P001 已过关闭时间 |

### 它能卡住哪类错误实现

| 错误类型 | 说明 |
|---------|------|
| **区间开/闭错误** | 若实现用 `open_time < time`（严格小于）而非 `open_time ≤ time`，12:00 会被误判为未开放 |
| **close_time 语义倒置** | 若实现将 `close_time` 理解为"关闭的开始"（即 `time ≥ close_time` 时关闭），恰好 12:00 时也会被误判为关闭 |
| 字符串比较代替时间比较 | 若用字符串字典序直接比较 `"12:00" <= "11:59"`（而非解析为分钟数做数值比较），结果完全错误 |

### 我的程序如何正确处理

`makeTimeFilter` 返回的过滤条件是 `place->open_time <= time_str && time_str <= place->close_time`，两端均为 **`≤`（闭区间）**。时间字符串首先校验 `HH:MM` 格式，再转为分钟数（`HH*60 + MM`）做整数比较，不存在开闭区间歧义或字典序陷阱。

### 测试结果

```
PASS — 12:00 可达，11:59 和 12:01 均正确返回 NO_PATH
```

## 用例 D：桥与割点 — `D_bridge`

### 这组数据特殊在什么地方

图由一个**线形链**和末端的一个**三角形**拼接而成：

```
P001 ── P002 ── P003 ── P004
                \       /
                 └─ P005 ─┘   (三角形)
```

关键结构：
- P001–P002：**桥** — 移除后 P001 孤立（无任何替代路径）
- P002–P003：**桥** — 线上唯一切割点间的唯一边
- P003–P004、P004–P005、P005–P003：三角形三条边，**都不是桥** — 三角形中任一边被移除都有另一条替代路径
- P002、P003：**割点** — 移除后均增加连通分量数
- P001：度数为 1 但不是割点（移除后剩 4 个连通节点）—— 常被初学者误判

### 它能卡住哪类错误实现

| 错误类型 | 说明 |
|---------|------|
| **三角形边误判为桥** | Tarjan 桥判定条件为 `low[v] > disc[u]`（严格大于）。若实现用 `low[v] >= disc[u]` 或未正确处理回边，三角形边会被误标记为桥 |
| **叶节点误判为割点** | 度数为 1 的节点（P001）移除后剩余图仍连通，不是割点。若实现仅以度数 1 判定，会误判 |
| **割点漏判** | 若实现仅以度数判定割点（如认为度数 ≥ 2 即是），则可能将 P004、P005 误判；或遗漏 P002（需检查 low[v] ≥ disc[u]） |

### 我的程序如何正确处理

`computeCritical` 使用标准 Tarjan 算法：
- **桥判定**：`low[v] > disc[u]`（严格大于）——确保 v 的子树中没有任何回边能到达 u 或 u 的祖先。三角形中的回边会使 `low[v] ≤ disc[u]`，从而正确排除
- **割点判定**：对非根节点检查 `low[v] >= disc[u]`；对根节点检查 `children > 1`。P001 作为叶节点（parent=-1 的子节点），children=1，不满足割点条件
- 桥边收集后标准化为 `from_id <= to_id` 并按字典序排序输出

### 测试结果

```
PASS — 正确识别 2 个割点和 2 座桥，三角形边未被误判
```

## 用例 E：孤立点 — `E_isolated`

### 这组数据特殊在什么地方

10 个顶点中只有 P001–P002–P003 构成唯一连通分量（大小 3），其余 7 个顶点（P004–P010）全部是**无边孤立点**。这种极端稀疏图同时检验连通分量分析、关键节点/边检测、以及最小生成树对不连通图的处理。关键边界：孤立顶点不是割点（移除后不增加分量数），也不是桥的端点（无边可移除）。

```
P001 ── P002 ── P003   (唯一连通分量，3 节点 2 边)
P004  P005  P006  P007  P008  P009  P010  (7 个孤立顶点)
```

| 输出 | 值 |
|------|-----|
| `COMPONENTS` | `8 SIZES 3 1 1 1 1 1 1 1` |
| `CRITICAL NODES` | `1 P002` |
| `CRITICAL EDGES` | `2 P001-P002 P002-P003` |
| `MST` | `DISCONNECTED` |

### 它能卡住哪类错误实现

| 错误类型 | 说明 |
|---------|------|
| **孤立点误判为割点** | 孤立点 DFS 中 parent=-1 且 children=0。若实现仅以"parent==-1"判定割点而未检查 children>1，会将所有孤立点误报为割点 |
| **COMPONENTS 遗漏孤立点** | 若 BFS/DFS 仅遍历邻接表中的节点，无边节点可能不被访问，导致分量数少计 |
| **MST 错判连通** | 若 Kruskal 实现仅比较 `edges.size() >= V-1` 而不通过 DSU 校验全图连通，可能对不连通图输出错误 MST |
| **分量大小未排序** | 规范要求分量大小降序排列；若未排序，输出顺序可能不稳定 |

### 我的程序如何正确处理

- **COMPONENTS**：遍历 `getAllVertexIds()`（返回所有顶点，含无边孤立点），对每个未访问顶点启动 BFS，确保孤立点也被计数。分量大小收集后用 `std::greater<>()` 降序排列
- **CRITICAL**：Tarjan 算法对孤立根节点（`parent=-1, children=0`）的判定：非根节点检查 `low[v] >= disc[u]`，根节点检查 `children > 1`——孤立点的 children=0 不满足条件，不会被误判
- **MST**：Kruskal 后显式检查 `edges.size() == V-1`（本例 2 ≠ 9），不满足则 `connected=false`，输出 `DISCONNECTED`

### 测试结果

```
PASS — 8 个分量正确识别，孤立点未被误判为割点
```
