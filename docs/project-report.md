## 1. 数据结构设计说明

### 1.1 存储结构选型

本项目的图存储层 `LGraph` 采用了 **邻接表 + 哈希索引** 的组合方案：

```
LGraph
├── unordered_map<string, Place> places_         // place_id → Place 结构体
├── unordered_map<string, vector<Road>> adj_     // place_id → 邻接边列表
└── unordered_set<string> edge_keys_            // 标准化边键 "min|max"，用于 O(1) 判重
```

**核心字段说明**：

| 成员 | 类型 | 用途 |
|------|------|------|
| `places_` | `unordered_map<string, Place>` | 顶点存储，支持 O(1) 按 ID 查询/增删 |
| `adj_` | `unordered_map<string, vector<Road>>` | 邻接表，无向边存储为两条有向记录 |
| `edge_keys_` | `unordered_set<string>` | 边唯一性判定，键为 `min(id1,id2) + "\|" + max(id1,id2)` |

### 1.2 设计考量与替代方案

| 维度 | 选用方案 | 备选方案 | 权衡 |
|------|---------|---------|------|
| **顶点存储** | `unordered_map` | `map`（红黑树） | 哈希表 O(1) 平均查找 vs O(log n)；字典序遍历需求通过临时 `sort` 解决 |
| **邻接存储** | 邻接表 | 邻接矩阵 | 图稀疏（E ≪ V²），邻接表空间 O(V+E) 远优于矩阵 O(V²)；Dijkstra 遍历邻居时也只需遍历实际存在的边 |
| **边判重** | `unordered_set` 标准化键 | 遍历邻接表 | O(1) vs O(degree)，增删道路操作频繁时哈希判重优势明显 |
| **删除策略** | 惰性索引 + 遍历删除 | 标记删除 | 地点删除时遍历其邻接表，从对方邻接表中移除对应边；简单可靠，数据量不大时性能可接受 |
| **无向图表示** | 双向存储 | 单向 + 自动取反 | 双向存储使邻接查询 O(1)，代价是增删时需操作两处 |

### 1.3 设计质量

- **增删改查复杂度**：顶点操作 O(1)（哈希表）；道路增删 O(degree)（遍历涉及的邻接表）；判重 O(1)
- **边界处理**：`addPlace` 拒绝重复 ID；`deletePlace` 级联删除关联道路；`addRoad` 标准化端点（`from_id ≤ to_id`）并拒绝自环和多存同一条道路
- **兼容性**：同一套 `LGraph` 结构无缝支撑所有必做功能（Dijkstra、Kruskal、Tarjan、BFS）和三个拓展任务（分层图、自定义数据、GUI），无需任何结构变更

### 1.4 辅助数据结构

- **DSU（并查集）**：`unordered_map<string, string> parent_`，使用路径压缩，用于 Kruskal MST
- **优先队列**：`std::priority_queue<pair<int, string>, vector<...>, greater<>>`，Dijkstra 核心。`pair<int, string>` 在代价相同时按 `string` 字典序出队，保证路径确定性
- **结果结构体**：`PathResult`、`MSTResult`、`CriticalResult`、`KPathResult`，分离算法输出与格式化逻辑

## 2. 关键算法说明与复杂度分析

### 2.1 Dijkstra 最短路径

**实现思路**：通用化设计，通过 `WeightFunc`（权重提取函数）和 `VertexFilter`（顶点过滤器）参数化。DIST 模式 `weightFunc` 返回 `road.distance`，TIME 模式返回 `road.walk_time`。TIMED_SHORTEST 通过 `makeTimeFilter` 构造开放时间过滤器（闭区间 `open_time ≤ HH:MM ≤ close_time`）。

**关键细节**：
- 优先队列使用 `pair<int, string>` + `greater<>`：代价相同时顶点 ID 字典序决定出队顺序，保证输出确定性
- 起终点在 `vertexFilter` 或 `placeExists` 检查失败时返回不可达
- 路径回溯：从终点通过 `prev` 映射反向追踪到起点，再 `reverse`

**复杂度**：时间 O((V+E) log V)，空间 O(V+E)

### 2.2 连通分量分析（BFS）

**实现思路**：遍历 `getAllVertexIds()`（含孤立点），对每个未访问顶点启动 BFS，仅沿 `open` 边扩展。分量大小用 `std::greater<>()` 降序排列。

**复杂度**：时间 O(V+E)，空间 O(V)

### 2.3 时刻约束最短路径

**实现思路**：复用通用 Dijkstra，通过 `makeTimeFilter` 构造闭区间过滤器（`open_time ≤ time ≤ close_time`）。字符串 `HH:MM` 转换为分钟数做整数比较，避免字典序陷阱。

**起点/终点特殊处理**：若起点/终点在查询时刻不开放，Dijkstra 入口即返回 `NO_PATH`。

**复杂度**：同 Dijkstra，O((V+E) log V)

### 2.4 必经点路径（MUST_PASS）

**实现思路**：将 `{from, p1, p2, ..., pk, to}` 拼接为点序列，严格按顺序逐段调用 Dijkstra。拼接时跳过重复的段间节点（前段终点 = 后段起点）。任一段不可达则整体 `NO_PATH`。

**关键设计**：不排序、不去重、不全排列——严格尊重用户指定的必经点顺序。

**复杂度**：O((k+1) · (V+E) log V)，k 为必经点个数

### 2.5 最小生成树（Kruskal）

**实现思路**：
1. 收集所有 `open` 边，按 `distance` 升序排序
2. DSU 贪心选边，不形成环则加入
3. 检查 `edges.size() == V-1` 判定连通性

**选择理由**：Kruskal 天然处理不连通图（边数不足时直接判定 `DISCONNECTED`），且对稀疏图效率高。Prim 需要额外的连通性检查步骤。

**复杂度**：时间 O(E log E)（排序主导），空间 O(V+E)

### 2.6 关键节点与关键边（Tarjan）

**实现思路**：采用 Tarjan 算法一次 DFS 同时求割点和桥，而非朴素 O(V·(V+E)) 暴力法。

**核心判定条件**：
- **桥**：`low[v] > disc[u]`（严格大于），确保无回边到达 u 或更早祖先
- **割点（根节点）**：`parent == -1 && children > 1`
- **割点（非根节点）**：`low[v] >= disc[u]`
- **孤立点处理**：`parent == -1, children == 0` 不满足割点条件

**复杂度**：时间 O(V+E)，空间 O(V+E)

### 2.7 分层图最短路（SHORTEST_K，拓展 1）

**实现思路**：将状态建模为 `(place_id, used)`，共 K+1 层：
- 同层转移（不用券）：代价 +`walk_time`
- 跨层转移（用券）：代价 +`ceil(walk_time/3)`
- 使用 `unordered_map<State, int>` 作为距离数组，自定义哈希

**回溯策略**：到达终点后在所有层（0~K）中找最优状态，反向回溯收集节点序列和用券边（标准化 + 字典序排序）。

**K=0 退化**：直接委托给普通 Dijkstra（TIME 模式）。

**复杂度**：时间 O((K+1) · (V+E) · log((K+1)V))，K ≤ 10，空间 O((K+1)·V)（实际上不同层的状态总数远小于 (K+1)·V）

### 2.8 算法汇总

| 算法 | 时间复杂度 | 空间复杂度 | 核心数据结构 |
|------|-----------|-----------|-------------|
| Dijkstra | O((V+E) log V) | O(V+E) | 优先队列 + 哈希表 |
| BFS 连通分量 | O(V+E) | O(V) | 队列 + 集合 |
| MUST_PASS | O(k·(V+E) log V) | O(V+E) | 复用 Dijkstra |
| Kruskal MST | O(E log E) | O(V+E) | DSU（路径压缩） |
| Tarjan 割点/桥 | O(V+E) | O(V+E) | DFS 递归栈 + 时间戳数组 |
| 分层图最短路 | O((K+1)·(V+E)·log((K+1)V)) | O((K+1)·V) | 状态优先队列 |

## 4. 遇到的问题与解决思路

### 4.1 测试程序比较逻辑过于宽松

**问题**：Copilot 生成的初始测试程序中，`compareMstLines` 仅校验总距离，完全忽略边数与边内容；`comparePathLines` 对 MUST_PASS 仅校验首末节点，不验证必经点是否被访问。13 个用例全部通过，但测试的有效性存疑。

**解决**：通过 Claude 分析发现三个显著漏洞后，修复了 MST 边数检查、新增了 CRITICAL 集合比较、添加了进程超时机制。PATH 比较保持宽松（允许等代价替代路径），MUST_PASS 必经点验证受限于架构约束（需解析 command.txt），在当前依赖参考输出逐行比对的框架下暂时无法实现完美的子序列检查。

### 4.2 SHORTEST_K 三个连锁 Bug

**问题**：探索测试全部失败，分析发现三个 bug：
1. **路径回溯遗漏起始节点**：回溯循环在遇到无前驱状态时退出，但未将起始节点加入路径
2. **可达性检查硬编码 3 层**：只检查 `{to, 0/1/2}` 而忽略层 3~K
3. **用券分支缺少 open 检查**：不使用券的路径检查了 `edge.status == "open"`，但用券分支缺少此检查

**解决**：手动修复所有三个问题。其中可达性检查改为遍历全部 K+1 层，用券分支补充 `if (edge.status != "open") continue`。

### 4.3 券加速公式的语义差异

**问题**：`walk_time / 3`（整除截断）与参考答案的 `ceil(walk_time/3)`（向上取整）不一致。walk_time=10 时 floor=3、ceil=4；walk_time=1 时 floor=0、ceil=1。系统性导致 totalTime 偏低 usedK。

**解决**：修改为 `(walk_time + 2) / 3`（整数向上取整），与规范"缩短为 ceil(walk_time/3)"一致。

### 4.4 Qt GUI 编译与运行问题

**问题 1**：`cmake --preset gui` 在 VSCode 终端中失败。根因是 `CMakePresets.json` 使用 `$env{QT6_MINGW_PATH}` 引用环境变量，但 VSCode 终端中未设置这些变量，CMake 展开为空字符串。

**解决**：将 Qt 路径硬编码到 `CMakePresets.json` 的 `gui` preset 中，删除对环境变量的依赖。

**问题 2**：GUI exe 运行时静默退出（VSCode 终端）或报错找不到 DLL（CMD 终端）。根因是 Qt DLL 不在系统 PATH 中。

**解决**：在 `CMakeLists.txt` 中添加 `add_custom_command(TARGET ... POST_BUILD)`，编译后自动运行 `windeployqt` 部署所需 DLL 到 exe 同目录。

### 4.5 C++17 Lambda 不可默认构造

**问题**：GCC 10.3.0 严格遵循 C++17 标准，拒绝编译 `unordered_map<State, int, decltype(hashState)> dist(0)`，因为 lambda 类型在 C++17 中不可默认构造（此特性在 C++20 才引入）。

**解决**：将 `dist(0, hashState)` 和 `prev(0, hashState)` 传入哈希函数实例。

#### 对话 1：项目讲解与九阶段工程计划

### B. 调试故事（3 个）

---

#### 调试故事 1：SHORTEST_K 起始节点丢失

**Bug 现象**：
- 输入：`SHORTEST_K P0001 P0004 1`，图数据见 `case_layered_01`
- 期望输出：`PATH 22 K_USED 1 NODES P0001 P0005 P0004 FAST 1 P0004-P0005`
- 实际输出：`PATH 21 K_USED 1 NODES P0005 P0004 FAST 1 P0004-P0005`（缺少 P0001，totalTime 少 1）

**我提供的诊断信息**：测试框架对比实际输出与期望输出，显示首节点不匹配（P0005 vs P0001）且总时间偏低。

**AI 的诊断过程与修复建议**：AI 通过对比 `dijkstra` 函数（正确地在循环后 `push_back(from)`）和 `shortestPathWithK` 函数（仅在 `prev.count(s) > 0` 时推入节点），精确定位到回溯循环在遇到无前驱的起始状态时退出，但未将起始节点加入路径。

**最终采纳方案**：在 `shortestPathWithK` 的回溯循环后添加 `path.push_back(s.first)`，与 `dijkstra` 的行为保持一致。完全按 AI 建议修复。

---

#### 调试故事 2：可达性检查硬编码 3 层

**Bug 现象**：`grid_100` 用例 K=8 时程序错误输出 `NO_PATH`，但实际存在需要 3 张以上券的可行路径。`random_sparse_1000` K=10 时有类似问题。

**我提供的诊断信息**：测试全部 4 个 explore 用例失败，实际输出显示 `NO_PATH` 而期望输出有路径。

**AI 的诊断过程与修复建议**：AI 搜索到 `shortestPathWithK` 中的可达性检查代码——硬编码为 `if (dist.count({to, 0}) == 0 && dist.count({to, 1}) == 0 && dist.count({to, 2}) == 0)`，仅检查 0~2 层，忽略了层 3~K。AI 建议改为循环检查全部 K+1 层。

**最终采纳方案**：改为 `for (int used = 0; used <= K; ++used)` 遍历检查。完全按 AI 建议修复。

---

#### 调试故事 3：GUI 运行时 DLL 缺失导致静默退出

**Bug 现象**：GUI exe 编译成功，但在 VSCode 终端中运行 `.\build-gui\CampusNavigation.exe --gui` 时无任何输出、无窗口弹出（进程静默退出）。在标准 CMD 终端中报错"无法找到 Qt6Widgets.dll"。

**我提供的诊断信息**：描述了两种终端的不同表现，以及 Qt 安装路径信息。

**AI 的诊断过程与修复建议**：AI 确认原因是 Qt DLL（`Qt6Widgets.dll`、`Qt6Core.dll`、`Qt6Gui.dll`）位于 Qt 安装目录的 `bin/` 下，不在系统 PATH 中。建议在 `CMakeLists.txt` 中添加 `add_custom_command(TARGET ... POST_BUILD)` 调用 `windeployqt` 自动部署 DLL。

**最终采纳方案**：在 CMakeLists.txt 的 GUI 配置块末尾添加了 `windeployqt --no-translations` 作为 POST_BUILD 步骤。编译后 DLL 自动复制到 exe 同目录，无需任何手动操作。完全按 AI 建议修复。

### C. 我拒绝过 AI 的建议（2 条）

---

#### 拒绝 1：PATH 行比较逻辑的过度严格化

**AI 当时建议什么**：在修复测试程序时，AI 建议对 `comparePathLines` 添加子序列检查（验证必经点是否出现在路径中）和节点数量检查（`actualTokens.size() == expectedTokens.size()`），以解决 MUST_PASS 必经点未被验证的问题。

**我为什么不采纳**：编译运行后发现 4 个误报（grid_100、ring_100、random_sparse_100、random_sparse_10000）——这些用例存在多条等代价替代路径（如不同的中间节点但相同总代价），节点数相同但节点序列不同是**合法**的正确行为。严格的节点数检查在 grid 类等权图中不适用。

**我的替代方案**：回退到原始行为（模式 + 代价 + 首/末节点），接受 MUST_PASS 必经点验证在当前"逐行对比参考输出"的测试框架中是一个已知局限。若要修复，需解析 `command.txt` 识别 MUST_PASS 参数——这是更重大的架构变更，不值得为测试框架投入此复杂度。此外，对抗样例 B（必经点顺序）通过独立的端到端测试覆盖了这一风险。

---

#### 拒绝 2：过度抽象的环境配置方案

**AI 当时建议什么**：在 GUI 集成初期，AI 设计了 `CMakeUserPresets.json.example` + `scripts/setup-qt-env.sh` + `scripts/setup-qt-env.bat` 三层配置方案，通过环境变量 `QT6_MINGW_PATH` 和 `QT6_MINGW_TOOLS_PATH` 引用 Qt 路径，意图实现"跨机器可移植"。

**我为什么不采纳**：
1. 三层抽象对单人项目过度设计，增加了理解负担
2. 环境变量方案在 VSCode 终端中天然不可靠（需要额外配置终端环境）
3. "可移植性"的代价是每个新开发者需要理解并设置 3 个文件，实际降低了可移植性

**我的替代方案**：直接将 Qt 路径硬编码到 `CMakePresets.json` 的 `gui` preset 中，删除 scripts 目录和 `.example` 文件。其他机器使用时只需编辑 `CMakePresets.json` 中 3 行路径即可（文档中明确说明）。这一方案在后续对话中被 AI 自己评价为"精简做的很不错"、"直接 `cmake --preset gui` 即可，无需任何前置设置"。

- **调试助手**：在 DLL 缺失、编译错误、运行时异常等场景下，AI 通过系统性诊断快速定位根因
